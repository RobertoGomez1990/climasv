## Por qué Server Components y Client Components

| Parte | Tipo | Razón |
| --- | --- | --- |
| Páginas `/`, `/ciudades`, `/acerca` y estructura de `/clima`; `Header`, `Footer`, estados de carga de segmentos | Server Components | Contenido estático o estructura de ruta sin estado del navegador; evita enviar JS innecesario. `/clima/page.tsx` lee el parámetro `city` y pasa un slug permitido al panel. |
| `src/app/api/weather/route.ts` y `src/lib/weather.ts` | Servidor (Route Handler y módulo) | El proveedor externo se consulta en backend, donde se valida el slug, se limita el tiempo y se normaliza la respuesta. No es un componente React. |
| `WeatherDashboard` y sus componentes importados (`WeatherCard`, `ForecastList`) | Client Component y su árbol cliente | Selector, `useState`, `useEffect`, petición con `AbortController`, reintento y datos que llegan después de hidratar. Las tarjetas se incluyen en ese árbol aunque no declaren `"use client"` por separado. |
| `CityExplorer` | Client Component | Búsqueda, filtro y favoritos en `localStorage`; `useSyncExternalStore` evita diferencias entre HTML inicial y cliente. |
| `MobileNavigation`, `RouteError` y archivos `error.tsx` | Client Components | Cierre del menú al pulsar un enlace y botones `reset()` de las fronteras de error requieren eventos; el Header completo no se hizo cliente. |

Las respuestas de error esperadas de la API se muestran dentro de `WeatherDashboard`; `error.tsx` cubre errores inesperados de las rutas. `loading.tsx` cubre navegación y el estado de carga del `fetch` cliente se muestra dentro del panel.

## Decisiones de la Etapa 3

- `src/lib/cities.ts` es la fuente única de nombres, departamentos, slugs y coordenadas; las fichas editoriales la reutilizan. Las coordenadas son puntos aproximados de referencia y no direcciones exactas.
- `OPEN_METEO_BASE_URL` es opcional y solo se lee en el servidor. El valor predeterminado es `https://api.open-meteo.com`; `.env.example` lo documenta y no hay claves de API. La URL se construye con coordenadas del catálogo, nunca a partir de una URL proporcionada por el visitante.
- Se solicitan explícitamente °C, km/h, hora local y cinco días. Se validan campos y longitudes antes de normalizar; el navegador no recibe el JSON completo de Open-Meteo. Se usa `cache: "no-store"` y un límite de 8 segundos. Un error HTTP o datos incompletos del proveedor se traducen a 502; timeout y fallo de red, a 503.
- La respuesta `city` es un objeto `{ slug, name }` para facilitar las futuras vistas; `current` y `forecast` contienen únicamente datos normalizados.

## Decisiones de la Etapa 4

- El parámetro `?city=` se valida en la página servidor y se pasa como slug inicial al panel cliente. El selector cancela la petición anterior al cambiar de ciudad; «Reintentar» dispara una consulta nueva sin mostrar cifras antiguas como si fueran actuales.
- Los favoritos se leen con `useSyncExternalStore`: el servidor y la primera renderización cliente ven `[]`, y después se sincronizan con `localStorage`. Solo se guardan slugs reconocidos. Se escuchan cambios de otras pestañas y se avisa si el almacenamiento falla.
- `error.tsx` cubre errores inesperados de ruta; las respuestas fallidas esperadas de la API se presentan dentro de `WeatherDashboard` con su propio botón de reintento. Los estados `loading.tsx` son de navegación; la carga del `fetch` cliente se muestra dentro del panel.
